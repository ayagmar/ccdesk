# Splitting the core from the web server

ccdesk's reading and writing code should be usable without the HTTP server, so that a command-line tool and a terminal UI can sit beside the web page and share it. This plan lists the steps in order. Each step keeps `pnpm check` green and ships on its own. [ARCHITECTURE.md](../ARCHITECTURE.md) describes the code as it is now.

## Decision: one package with subpath exports first

The core stays a folder in this package, reached through `exports` subpaths in `package.json` (`ccdesk` for the core and `ccdesk/view` for the rows). It becomes a separate workspace package only when a CLI or TUI needs to be released on a different schedule from the web app. Until then a split would mean changing the test glob, both tsconfigs, Biome's file list, the release workflow, release-it's config and the data workflow's `git add` list together, for no user-visible gain.

## Done

These landed after v0.2.2.

- **The core is importable.** `src/core/index.ts` re-exports the scan, the watcher, every preview and save, backups, the errors and the shared types. The build emits declarations, `package.json` maps `"."` to `dist/core` with its types, and CI imports the packed package. Test: `test/core.test.ts`.
- **Edit input is checked in the core.** The parsers that were in `server.ts` are `parseSettingsEdit`, `parsePermissionEdit`, `parseHookEdit`, `parseAgentEdit` and `parseMcpEdit` in `src/core/parse-edit.ts`, throwing `InvalidEditError` (400). Planning a hook edit already refused unknown events. Test: `test/core-parse.test.ts`.
- **A core-level round trip.** `test/core-edits.test.ts` saves and undoes a permission edit through the core. Settings, agent, project MCP and memory round trips stay in `test/server.test.ts`, whose routes pass edits straight to the same functions.
- **Generated data comes from the server.** The settings schema, catalog and hook events are exported from the core as `REFERENCE` and served by `/api/reference`, so the page no longer bundles them (913 kB to 496 kB).
- **The core has its seams (step 1).** `createCore(env, { runClaude?, openFile? })` in `src/core/core.ts` returns every read and change with `env` bound, and `createCcdeskServer` takes a core instead of `env`, `openFile` and `runClaude`. Each core makes its own change queue (`changeQueue()` in `write.ts`) and usage counter (`usageCounter()` in `scan/usage.ts`). `ScanEnv` gained `processEnv`, the environment ccdesk finds an editor and `claude` in; `openInEditor`, its `launch`, and `claudeRunner(env)` (which replaces `runClaude`'s body) take the platform and environment from it, and `claudeProgram` lost its `process` defaults. The free save functions take an optional queue as their last argument and `openInEditor` an optional host, defaulting to the process-wide queue and `process`; `readUsage` and `runClaude` use a process-wide counter and `process`. Existing calls still work; remove these defaults and wrappers one release later. The compiled schema validators in `settings-edit.ts` stay in module scope: they come from the bundled schema and never differ between cores, and Ajv caches compiled schemas itself. Tests: `test/core-instances.test.ts` (a save on one core does not wait for another core's; one core's usage count does not evict another's cache; a `win32` env opens a `.cmd` editor through `cmd.exe` and runs the `claude.exe` behind npm's `claude.cmd`, with the env's environment).
- **The CLI is split (step 2).** `parse(argv)` in `src/server/args.ts` turns the arguments into `{ command: "help" }` or `{ command: "serve", port, configDir, open, dev }` and throws `UsageError` with the message to print; it reads no files, so the bin still checks that `--config-dir` is a folder. `startServer(options)` in `src/server/start.ts` takes the server's options (a core, the launch folder, the token, `uiDir`) and a port, listens on 127.0.0.1, and resolves `{ url, close }`, or rejects when it cannot listen. `cli.ts` is now the short bin that wires them together and prints. The browser opens through `openBrowser(url, host)` in `open.ts`, which uses the same `launch` as the editor with the core's `env`; it now also reports an opener that exits with an error, such as `xdg-open` with no browser set, where the old launcher only reported one that failed to start. Test: `test/cli.test.ts` (the default and each flag, `--dev`'s port, refused ports and unknown flags, a server started with `uiDir: null` that answers at its URL and closes with a kept-alive connection open, and a port in use).
- **The files are moved (step 3).** The scan, the edit modules, `parse-edit.ts`, `write.ts`, `backups.ts`, `watch.ts`, `secrets.ts`, `schema.ts`, `reference.ts` and `open.ts` moved from `src/server` to `src/core` with `git mv`; `src/server` keeps `server.ts`, `start.ts`, `args.ts` and `cli.ts`, and `src/core` imports nothing from it. `scan/files.ts` is split three ways: it keeps file reading, the git calls are in `scan/git.ts`, and redaction (`redactSecrets`, `shownUrl`, `shownArgs`, `shownText`, `jsonSyntaxError`) joined `secrets.ts`. Outside import lines, the only change is `export` on `shownJsonFile`, which `files.ts` now takes from `secrets.ts`. `isRecord` and frontmatter parsing, which both need, are in `scan/data.ts`, so `files.ts` and `secrets.ts` do not import each other. `tsconfig.build.json` needed no change, since `src/core/**/*.ts` already covers the new folders. Tests that imported moved modules by path now import them from `src/core`; no test changed otherwise.
- **The view logic is out of React (step 4).** `src/view` imports no React and is exported as `ccdesk/view`. Each section's data half (`rows`, `columns` and their sort keys, `text`, `label`, `heading`, `dimmed`, `facet`, `empty`, `tableClass`) is a `ViewSection` in `src/view/sections/`, with `SECTIONS` and `buildRows`; `src/ui/sections/*.tsx` keep `cells`, `Head`, `Details` and the memory facet's `renderFacet` as a `SectionUi`, and `src/ui/sections/index.ts` joins the two by section id, so the page order is listed once. `rows`, `label`, `heading` and `facet.order` take a `ViewContext`, `{ format, reference }`, since the instruction labels show paths from the home folder and the catalog's rows and areas come from the settings reference; the page builds its own with `pageContext()`. `valueHere`, `outcome`, `callsOf`, `isSuggested` and `unused` moved with their sections; `lines.ts`, `diff.ts` and `usage.ts` moved whole; `fieldKind` and `valuesIn` are in `src/view/settings.ts`. `formatter(home)` in `src/view/format.ts` replaces `setHome`. The page still keeps one formatter in `src/ui/format.ts`, set by `useConfig` when the overview arrives, so its components did not change. `test/catalog.test.ts` and `test/diff.test.ts` stay in `test/` (the test glob is `./test/*.test.ts`) and import from `src/view/index.ts`. CI imports `ccdesk/view` from the packed package. Test: `test/view.test.ts` (every section builds rows from a scanned fixture with the core's `REFERENCE`, row ids are unique, and labels use the home folder each caller passes). The built page was compared in headless Chromium against the site's made-up demo home, before and after: the same rows, bullets, faded rows, facets, sort orders, inspector headings and palette labels.
- **Changes can be pushed (step 5).** `Watcher.subscribe(dir, onChange)` resolves, once the watchers of `dir` have started, to a function that unsubscribes. `onChange` is called once per settled change, from the same timer that answers waiting `wait()` calls, until it unsubscribes. The subscription shares the waiters' watchers and keeps them from going idle; after the last waiter and subscriber leave, they close after the same idle minute as before. `close()` stops the calls without making one, while it still answers each waiting `wait()`. The private method that started the watchers was named `subscribe`; it is now `watching`. `/api/watch` and the page are unchanged; pushing over server-sent events is the separate [feature idea](feature-ideas.md). Tests in `test/watch.test.ts`: two writes 100 ms apart reach a subscriber as one call and a write after unsubscribing reaches it not at all, and closing the watcher calls no subscriber.
- **A CLI on the core (step 6).** `ccdesk scan [dir] --json` prints the `DirectoryView` the page gets for a directory, and `ccdesk explain <file> [--dir <dir>]` prints what `testPath` finds, in the page's words: scope, kind (`MATCH_KIND`, now in `src/view/path-test.ts` and shared with the page), the file relative to the start folder or the skill's name, and the glob. `parse` returns `{ command: "scan", dir, configDir }` and `{ command: "explain", file, dir, configDir }`; each command takes only its own flags, so `ccdesk --json` or `ccdesk scan --port 80` is refused rather than ignored, and `scan` without `--json` is refused to leave room for a text format. `dir` and `file` are relative to the current directory, as a shell user expects, and `cli.ts` checks that the folder exists. The two commands are in `src/server/commands.ts`, which imports only `src/core/index.ts` and `src/view`; `cli.ts` loads `start.ts`, and through it the server, with `import()` only to serve the page. Both only read: the scan is already redacted, and `explain` prints only paths, names and globs the page shows. Tests in `test/cli.test.ts`: each command's arguments and the flags it refuses; `scan` on a fixture whose settings hold an API key under `env` prints the view without it; `explain` on a fixture prints the rule, folder instructions and skill with their globs, says when nothing more loads, and says when the file is outside the start folder. CI's smoke test deletes the packed package's `server.js` and `start.js` after loading the page, then runs both commands on a project.

- **The process-wide defaults are gone.** For the release after v0.2.3, as step 1 planned, the free `readUsage`, `runClaude` and `serially` are removed, `openInEditor` needs its host, and every save, restore and memory change needs its queue. The package exports those changes, and usage counts, only as a core's methods; reads and previews stay free functions. Tests that called the free functions now make a core, or a `claudeRunner` with its own environment instead of changing `process.env`.

## What is left

More subcommands are listed in [feature ideas](feature-ideas.md): `compare`, `changes` and `undo`, and `rules --suggest`. A terminal UI can draw its rows from `ccdesk/view`.

Decide on workspace packages only if the CLI or a TUI needs a release schedule different from the web app's.
