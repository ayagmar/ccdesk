The Settings section lists every key set in any settings file that applies to the open directory, with the value Claude Code ends up using and the file it comes from.

## Which files are read

From highest precedence to lowest:

1. **Managed**: `managed-settings.json` in your organisation's managed folder, plus every `.json` file in its `managed-settings.d/` folder, merged in alphabetical order.
2. **Local**: `.claude/settings.local.json` at the root of the repository's main checkout, as Claude Code reads it. On Windows, outside git, or when the repository root is your home folder, it is the one in the open directory instead. An older local file left in the open directory is still read, below the root one.
3. **Project**: `.claude/settings.json` in the open directory.
4. **User**: `~/.claude/settings.json`, or `settings.json` in `$CLAUDE_CONFIG_DIR`.

Your organisation can also deliver managed settings from the claude.ai admin console (server-managed settings), through a macOS configuration profile, or in the Windows registry. ccdesk does not read those. Claude Code ranks the console's settings first, then the profile or the `HKLM` registry key, then the files above, and by default uses the first source that sets a policy. When the server-managed settings Claude Code keeps in `~/.claude/remote-settings.json` or a macOS profile is on disk, the page warns that the managed values it shows may not apply. Run `/status` in Claude Code to see which source it uses.

Managed settings that fail Claude Code's settings schema are shown as Claude Code applies them, not as written. Claude Code repairs them rather than skipping the file: it strips invalid list entries, reads a quoted `"true"` or `"false"` as that Boolean, removes a key set to `null`, enforces an invalid `allowedMcpServers` or other managed allowlist as an empty list, reads a switch such as `allowManagedPermissionRulesOnly` as its restrictive value, repairs `permissions`, `autoMode` and `sandbox` field by field (withholding their grants while a deny list beside them is invalid), and drops the rest. A note under the page header lists each repair; hover over one to see what the file says.

## How a value is decided

- For most keys the highest file wins. Lower values are listed in **Overrides**, struck through, with their own bullets.
- Lists merge across files, and objects merge key by key. Those rows say **merged** and show every file's bullet.
- Some keys are read only from certain files. Claude Code's settings reference says which, and a value in any other file is marked **ignored**, with the reason in the inspector.
- A few keys follow their own rule, which the inspector names: for some security switches the strictest value wins even from a lower file, each model in `modelSettings` takes its `effortLevel` from the highest file that sets one for it (a top-level `effortLevel` in a higher project, local or managed file outranks it) and runs at the lowest `maxEffortLevel` any file gives it, `availableModels` from managed settings replaces every other file's list, a project or local `defaultMode` of `auto` or `bypassPermissions` is ignored, and so are the `sandbox` fields Claude Code does not take from a file: a repository's settings that loosen a sandbox managed settings require, values a managed-only lock such as `allowManagedDomainsOnly` covers, and nested keys read only from user or managed settings. ccdesk does not check the locks that depend on which paths are denied.
- `env` variables Claude Code ignores are marked **ignored** by name: those a project or local file cannot set, such as `HOME`, `CLAUDE_CONFIG_DIR` and the variables that turn telemetry on or send it somewhere (an off value such as `OTEL_METRICS_EXPORTER=none` still applies), and those it reads only from the environment it starts in, such as `CLAUDE_CODE_PROJECT_DIR_NAME`, from any file.

Values under `env` and `headers` show as `•••`. See [Safety and privacy](../safety-and-privacy/).

## Changing a setting

Select a row to see every file that sets the key and the value Claude Code uses, then change it in the inspector:

1. Pick the file to write: **User**, **Project** or **Local**. Files Claude Code does not read the key from are shown but cannot be picked. Managed settings cannot be changed from ccdesk.
2. Enter the value. The field matches the setting's type in Claude Code's schema: a checkbox, a choice list, a number, text with the documented values one click away, one entry per line for lists of text, a button per value for lists the schema limits, such as `allowedProviders`, and a field per property for objects such as `autoMode` and `statusLine`. A property you leave empty is not written. Everything else is JSON, with a line saying what shape the value takes. A value the form cannot show exactly, such as an object with a property the schema does not name or text with a line break, is shown as JSON too, so saving never drops part of it. **Edit as JSON** switches a form to JSON, for a value the form cannot write, such as an empty list; **Edit in form** switches back when the form can hold the value. An `autoMode` list (`allow`, `soft_deny`, `environment` or `hard_deny`) without `"$defaults"` replaces Claude Code's built-in rules instead of adding to them, and an empty one, which only JSON can write, leaves that list with no rules at all. The editor warns about both, in the form and in JSON, and points to `claude auto-mode defaults` for copying the built-in rules if you mean to own the list; in the form, **Keep built-in entries** adds `"$defaults"` at the top.
3. Press **Review change** to see the diff of the file.
4. Press **Save**.

To add a key that is not set yet, use **Add setting** at the top of the section and pick the key; it suggests keys from the schema with their descriptions. **Remove from this file** deletes the key from the chosen file.

What happens on save:

- The value is checked against Claude Code's settings schema. If it fails, the errors are shown and there is no Save button.
- ccdesk writes exactly the reviewed change. If the file changed after you pressed **Review change**, it refuses and asks you to review again.
- Other keys stay as they were. If the file was not formatted with two-space indentation, ccdesk says it will reformat the whole file.
- The old file is copied to the backup folder first, and the change can be undone from the toast or from [Recent changes](../recent-changes/).
- If the settings file is a link, for example into a dotfiles repository, ccdesk writes through it and the link stays a link.

A key whose value holds hidden parts, such as a non-empty `env`, or an `allowedMcpServers` or `deniedMcpServers` entry with a token in its command, cannot be changed from ccdesk; edit it in the file. A settings file that is not valid JSON is listed at the top of the page with the line and column of the error, and ccdesk will not write to it until you fix it. A user, project or local file with a value Claude Code's settings schema rejects, such as text where a number belongs, is listed there too: Claude Code skips the whole file (an interactive session asks at startup whether to fix it, exit or continue without it; `claude -p` skips it without asking), so ccdesk shows the settings without it.

## Comparing two directories

**Compare with…** at the top of the section opens a picker: choose another directory Claude Code has been used in, or type the full path of any folder. The comparison page lists the keys whose values differ, with the value each directory ends up with and the files it comes from. **All** also shows the keys that are the same in both, dimmed. A value that Claude Code ignores in a directory counts as not set there.

Hidden values stay hidden, so ccdesk compares them as shown: two `env` entries that are both `•••` count as the same even when the real values differ. The page has its own address, so you can bookmark a comparison or reload it.

## All settings

The All settings section lists every key in Claude Code's settings reference, set or not, grouped by area. For each one it shows what the setting does, which files Claude Code reads it from, its documented values and default, and the value it has here. Select a key to read its documentation and, where ccdesk can write it, set it in the file you choose.

Some keys cannot be set from here: keys Claude Code keeps in `~/.claude.json` (use `/config` in Claude Code), managed-only keys, nested fields such as `sandbox.network.allowedDomains` (edit the parent key), and the few documented keys that no schema ccdesk ships with defines yet.

## Where the schema comes from

The schema is generated from the `Settings` type in [`@anthropic-ai/claude-agent-sdk`](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk), which is published with each Claude Code release. For documented keys that type leaves out, such as `autoMode`, ccdesk uses the definition from [SchemaStore](https://json.schemastore.org/claude-code-settings.json), and the editor says so under the key's description. Which files each key is read from, and the descriptions in All settings, come from the [settings reference](https://code.claude.com/docs/en/settings-reference). A daily job regenerates all of them; see [Contributing](../contributing/#claude-code-data).
